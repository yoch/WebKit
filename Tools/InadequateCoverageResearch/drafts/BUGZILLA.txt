Bug title:
[JSC] Reoptimize sooner on repeated same-site InadequateCoverage OSR exits

Product: WebKit
Component: JavaScriptCore

Description:

DFG/FTL plant ForceOSRExit (ExitKind::InadequateCoverage) for bytecode
whose value profile is still SpecNone. Once that site executes, every
subsequent execution that reaches the same ForceOSRExit site exits until
the CodeBlock is recompiled.

handleExitCounts() currently only jettisons when the *global*
CodeBlock::osrExitCounter exceeds osrExitCountForReoptimization (100)
or, for inlined-loop cases, osrExitCountForReoptimizationFromLoop (5).
A same-site phase change therefore burns ~101 deopts on the generic
budget. Distinct never-again sites should not share an aggressive
budget.

Proposal:
- Per-site trigger: OSRExit::m_count > dedicated
  osrExitCountForReoptimizationFromInadequateCoverage (default 5;
  compare is unsigned `count > threshold`, so the 6th same-site hit
  reoptimizes). Uses adjustedExitCountThreshold exponential backoff.
- The helper multiplies by codeTypeThresholdMultiplier() exactly as
  the generic and FromLoop helpers do (Eval × evalThresholdMultiplier,
  default 10; Function and Program × 1). Not a special-case divergence.
- Do not reuse FromLoop: that option means "stuck in a loop", and
  changing it would unexpectedly change non-loop InadequateCoverage
  policy. JSC already has a dedicated
  ftlOSREntryFailureCountForReoptimization for a similarly distinct
  trigger.

Default 5 is a conservative JIT heuristic, not "because FromLoop is 5":

- On a durable same-site phase change (20 reps), t=3/4/5/6 are
  indistinguishable (median ~0.68–0.69 ms). The extra 2 hits vs t=3
  cost a few tenths of a millisecond at most.
- t=5 avoids jettison on a 5-then-never burst and on 32 interleaved
  sites ×4 / ×5. t=3 jettisons both.
- OSRExit::m_count is cumulative and never decays. Rare spaced hits
  of the same site (10^3…10^6 warm calls between hits) fire at hit
  t+1 for every fixed threshold. t=5 buys two extra lifetime hits of
  slack versus t=3 before an unnecessary jettison. A decaying rate
  would be a redesign; this patch does not add one.

This is not a correctness bug. The current heuristic is safe but
leaves a newly hot uncovered site on the deopt stub for too long
(observed with FrozenMiniSearch-style update-after-insert workloads,
and independently with a two-arm `if (mode) return object.x` microbench).
