Reoptimize sooner on repeated same-site InadequateCoverage exits
https://bugs.webkit.org/show_bug.cgi?id=XXXXXX

Reviewed by NOBODY (OOPS!).

ForceOSRExit planted for SpecNone bytecode is deterministic: every
subsequent execution that reaches that ForceOSRExit site exits until
the CodeBlock is recompiled. The generic osrExitCountForReoptimization
budget (100) therefore leaves a newly hot previously-uncovered site
deoptimizing for ~101 calls.

Count repeats of that OSR exit's m_count against a dedicated
osrExitCountForReoptimizationFromInadequateCoverage threshold (default
3, same unsigned `count > threshold` convention and
adjustedExitCountThreshold / retry doubling as the existing counters).
Threshold 0/1/2 jettison a 32-site ×1/×2/×3 cold spray; 3 is the first
value that does not. Distinct sites keep independent counters so they
do not share this budget.

The option is dedicated rather than reused from
osrExitCountForReoptimizationFromLoop so that tuning the loop-stuck
budget does not silently change non-loop InadequateCoverage policy.
This matches the existing split between the generic, FromLoop, and
ftlOSREntryFailureCountForReoptimization knobs.
